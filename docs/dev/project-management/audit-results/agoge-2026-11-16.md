### 1 of 31 · HIGH · The model check passes for any model name, so a store can be labelled with one model and filled by another

**What.** Before embedding, engram asks the server which model it is and refuses a mismatch. Against a real llama-server that check cannot fail, because the server repeats back whatever model name the request carried. The check is in `src/engram/client.py`; heidi found it.

**Evidence.** Config set to `id = "acme/other-embed:Q8"` on a port where Qwen was serving: `engram index`, `query`, `index --rebuild` and `harvest` all returned rc 0, and the store meta read `embedding_model_id = acme/other-embed:Q8` with Qwen vectors inside. `GET /v1/models` on the same server reports the true id. The test fake in `tests/_embedding_server.py` answers with its own id, so the tests pass on a belief the real server does not hold. Confidence: confirmed.

**If unchanged.** Anyone who edits the model id while an old server still holds the port gets a store that claims the new model. Queries then compare vectors from two models and return poor matches with no error. It needs a config change to trigger, so it is rare, but nothing ever reports it.

**Options.**

2. **Record the served id in the store on every write** and refuse on drift. Benefit: catches the same error later too. Drawback: more state, and it does not stop the first bad write. Effort M. Risk: false refusals after a harmless alias rename.
3. **Refuse to lease a server engram did not spawn** when the id differs from the spawn command line. Benefit: no protocol dependence. Drawback: breaks the operator-run shared server case. Effort M. Risk: high for existing setups.
4. Accept or defer.

**Recommendation: option 1.** It fixes the check where it is and repairs the test that hid it. The strongest point against: `/v1/models` reports the alias, so a deliberately aliased server needs its alias in the config.
